# Create Table Designer Manual Test Log

Use this file to record manual validation scripts and provider-specific results for the create table designer.

The "Generated SQL" block under each provider is a reference script (table with a single-column primary key,
a foreign key with `ON DELETE`/`ON UPDATE`, and an index) produced by `TableDdlScriptBuilder` against the
integration seed schema (`customers`/`orders`, see `docker/integration`). The same scenario is covered by an
automated check in `DataDeveloper.Tests/Integration/TableDesignerIntegrationTests.cs`
(`RUN_DB_INTEGRATION_TESTS=1 dotnet test DataDeveloper.Tests/DataDeveloper.Tests.csproj --filter TableDesignerIntegrationTests`),
which applies the generated script against a real database, inserts a row, and drops the table. Use this file to
record the result of running that exact flow through the UI, plus any manual scenario from "Scenarios To Cover"
that the automated test does not exercise (composite keys, multiple FK column mappings, unique/descending indexes,
invalid-draft warnings, tab-switch persistence).

## Test Scope

- Generate a table with multiple columns.
- Use provider-specific data types.
- Create a primary key.
- Create a foreign key.
- Create an index.
- Apply the generated SQL from the designer.
- Copy and save the generated SQL when relevant.
- Confirm the schema explorer refreshes after a successful apply.

## Scenarios To Cover

- Basic table with no foreign keys or indexes.
- Table with identity/autoincrement primary key.
- Composite primary key.
- Foreign key with one column.
- Foreign key with multiple column mappings.
- Foreign key with referenced schema when the provider supports schemas.
- Foreign key with `ON DELETE`.
- Foreign key with `ON UPDATE` when the provider supports it.
- Index with one column.
- Index with multiple columns.
- Unique index.
- Index with descending column order when the provider supports it.
- Invalid FK/index draft should keep valid SQL visible and show warnings.
- Switching between Columns, FK, and Index tabs should preserve combo selections.
- Applying a script with multiple statements should execute each statement correctly.

## Provider-Specific Notes

- MySQL foreign keys require InnoDB on both the new table and the referenced table.
- Oracle execution through the app sends statements individually; copied/saved scripts may still include semicolons.
- SQLite has limited `ALTER TABLE` and provider-specific primary key/autoincrement behavior.
